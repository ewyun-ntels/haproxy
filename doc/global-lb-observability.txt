Global LB read-only operational diagnostics (step 10)
====================================================

UD-013 r1-observability-20261002. No runtime setter or network operation is
added to the CLI. Existing "show global-lb local" is unchanged.

  show global-lb status
    Requires USE_GLOBAL_LB, admin CLI level, no arguments. Reports enabled,
    effective cache state/usability/reason, transport state, instance-id,
    writer_generation, last submitted sequence, successful publications,
    failure events, untracked connections, cache version/endpoint count/age,
    last publication age, recovery progress, configured sync/stale interval,
    terminal shutdown state and cleanup result.

  show global-lb cache
    Requires USE_GLOBAL_LEASTCONN, admin CLI level, no arguments. Captures one
    complete published cache version into owned rows and outputs endpoint,
    cached global, same-cache own, current local absolute and adjusted count:

      global - cache_own + local_current

Age -1 denotes no successful publication/complete cache. Counts may remain
visible when unusable; FALLBACK/RECOVERING rows are diagnostic only. A non-enabled
worker reports DISABLED. Current local counts have connection-time cur_sess
semantics, identical to the selector and publisher; native served is not reset.
An incomplete registry or inconsistent arithmetic prints "unknown", never zero.

Cache keys/global/own values are copied under the cache read lock and remain
valid across later cache swaps while CLI output yields. Allocation/copy happens
only for the CLI, never on the server-selection path. Current local correction
is read for each output row and may evolve during a long CLI response. Runtime
status is a copied diagnostic view; independently changing cache/transport/local
fields are not a cross-component transactional snapshot. The cache command lists
published-cache keys, not every possible healthy server; absent endpoints are
still supported by the selector's zero-remote policy.

Logs
----
Worker-0 control-plane events log cache state transitions and their reason and
recovery count, plus terminal cleanup outcome, through HAProxy notices and its
configured global logging. Unchanged states do not produce repeated transition
logs. Staleness is evaluated on reads/events without an additional monitor task;
CLI state becomes stale at the deadline, while its transition log can wait for
the next client event. Existing error warnings remain transition-limited.

Example (Unix Runtime API socket):
  printf 'show global-lb status\n' | socat - /var/run/haproxy/admin.sock
  printf 'show global-lb cache\n'  | socat - /var/run/haproxy/admin.sock

Tests
-----

  SANITIZE=1 sh tests/unit/global-lb-collect.sh
  python3 tests/unit/global-lb-runtime.py ./haproxy valkey/valkey:9.1.1-alpine

Tests verify owned copied cache rows across invalidation, status identity and
counts, argument validation, ACTIVE/GRACE/stale fallback/recovery and preserved
traffic during store fencing. Feature-OFF builds contain no Global LB CLI code;
common-only builds provide status/local but no cache CLI or cache symbols.
