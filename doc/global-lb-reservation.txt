Global LB v2: reservation protocol and native hooks (steps 1-2)
=============================================================

User Define: UD-007/009/011 v2-r1-20261003; USE_GLOBAL_LB.
Configuration also implements UD-010 timer/migration validation.
This document supersedes v1 protocol assumptions only for reservation mode.

Implemented and not implemented
-------------------------------
Step 1 provides configuration, types, RESP2 builders/reply decoding and Lua.
Step 2 adds native stream/slot hooks, a serial metadata ledger and a dispatcher
on the EXISTING thread-0 client task. No extra task/thread/socket is created.
Production activation still awaits step 3's confirmed START/RESTORE lifecycle;
there is NO automatic v2 reservation I/O in a normal production binary yet.
An explicit v2-only timer selects staged reservation mode; the old snapshot
publisher is disabled, and opted-in Backends use native local leastconn.
A warning states that v2 runtime integration is pending. Do not describe this
binary/config as a working atomic Global LeastConn implementation yet.

During this staged migration, configs containing only v1/common directives
retain v1 behavior. The new timer fields always default to reserve=100ms,
heartbeat=300ms and instance-timeout=3000ms, but selecting v2 requires at least
one v2-only directive until runtime integration is completed. No new version
selector is invented. Mixing explicit v1 sync-interval/snapshot-ttl/stale-after/
recovery-successes with v2 timers is a configuration error, in either order.
The final v2 default-mode/migration switch is tracked separately, not silently
enabled before native reservation/release hooks are implemented.

Reservation lifecycle contract
------------------------------
Reuse the native HAProxy flow, not a second local served implementation:
  1. Lua chooses the minimum eligible endpoint and increments its global
     reservation contribution, storing request-id -> endpoint atomically.
  2. HAProxy sets s->target, then follows native srv->served acquisition and
     sess_change_server()/s->srv_conn registration. Lua cannot atomically write
     the local C structures. Failure to acquire the native slot cancels the
     global reservation. Queue/maxconn/health/backup policy stays native.
  3. TCP success does not increment again. Global release follows native slot
     release, failure/redispatch/cancel/stream destruction exactly once.
     A same-server retry that retains its native slot must not release/reserve
     twice. A redispatch that changes assignment drops the old reservation.
The stream metadata tracks the remote request, not an independent local count.
Those hooks, asynchronous wait/resume, deadlines and fallback dispatch are
implemented in step 2; automatic startup/HB/recovery/shutdown is still step 3.
The original cur_sess/served read-only Local Snapshot fields stay unchanged.
Health-check connections and unassigned queue entries are not global reserves.

Configuration
-------------
See examples/global-lb-v2-step1.cfg. New global directives:
    global-lb timeout reserve 100ms
    global-lb heartbeat-interval 300ms
    global-lb instance-timeout 3s
All accept the native duration units/range used by the existing parser.
instance-timeout must be strictly greater than heartbeat-interval.
state-store and instance-id remain required if any global-lb setting is used.
Existing connect=200ms, command=100ms, reconnect=100ms..5s, jitter=20% stay intact.
reserve timeout covers queued request + send + response and is wired in step 2.
Config changes require restart, not live reload. Default fallback is native LC.

Storage schema (standalone Redis/Valkey, four fixed Hash keys)
------------------------------------------------------------
For key-prefix ipmdn:global-lb the keys are:
    glb:v2:69706d646e3a676c6f62616c2d6c62:owners
    glb:v2:69706d646e3a676c6f62616c2d6c62:liveness
    glb:v2:69706d646e3a676c6f62616c2d6c62:counts
    glb:v2:69706d646e3a676c6f62616c2d6c62:requests
Prefix and instance IDs are hex-encoded. v1 keys are disjoint and untouched.
All four accessed keys are supplied in EVAL KEYS; no generated Redis key access,
KEYS command or SCAN discovery in the selection path. This is not Cluster support.

Using i = hex(ipmdn-prod/haproxy-0):
    owners[i]                   = writer_generation UUID
    liveness[i]                 = revision|heartbeat_ms|high_water|A/R/D
    counts[i|be_ipmdn_tcp|10.244.1.10:5000] = 12
    requests[i|request_id]       = be_ipmdn_tcp|10.244.1.10:5000
A=active, R=requires restore, D=terminal. UUID is created once per worker process
startup and never changed on state-store reconnect. No AUTH/TLS/USE_LUA/hiredis.
TIME supplies the store clock; counts/requests have no short TTL that could erase
an active long-lived TCP connection. Stale instance contribution is ignored once
its heartbeat age exceeds the configured timeout. Physical stale instance/data
reclamation is a later maintenance concern; it is not claimed implemented here.

Protocol and idempotency
------------------------
START/RESTORE: supply all active request-id/endpoint assignments and high_water.
Derive own counts from that ledger and atomically replace only own contribution.
The caller must include pending native slot reservations and fallback assignments,
not only successful cur_sess connections. The caller captures them consistently
and serializes capture/commit/local changes; that stream ledger is not in step 1.
START can replace another UUID (accepted R2 delayed initial START limitation).
RESTORE registers a missing owner, but never steals another UUID's owner.
Same UUID/revision replacement retry confirms without overwriting later deltas.
Fresh RESTORE advances revision; every reserve/release/cancel/HB/stop echoes it,
so delayed operations from before the replacement cannot change the new state.
Revisions are restore barriers, NOT newly generated writer UUIDs on reconnect.

RESERVE: candidates must be unique actual endpoint keys of one service/backend.
Only ACTIVE, fresh instances participate. Lua sums eligible endpoint counts,
chooses a minimum (equal weights; random ties seeded by caller), reserves +1 and
records its request ID. It returns the endpoint and global count after +1.
Duplicate active request returns its original endpoint/current global count
without +1, even if it is no longer in the refreshed candidate list; the caller
must revalidate health/identity and cancel instead of connecting if unsuitable.

RELEASE/CANCEL: a known request decrements once and removes its active mapping.
Unknown RELEASE is absent; unknown CANCEL advances the high-water fence. Released/
cancelled requests cannot be recreated by a delayed RESERVE. No completed-request
tombstone grows per connection: active mappings plus one monotonic per-writer
high_water are retained. New request IDs must increase at dispatch; out-of-order
older allocations may be rejected (safe fallback, not duplicate reservation).
IDs are not reset on reconnect. Duplicate active allocations remain replayable;
completed IDs <= high_water remain fenced. uint64 IDs/revisions are compared as
canonical decimal strings, preserving correctness above Lua's double precision.

HEARTBEAT: same UUID/revision and fresh ACTIVE state only. Expired instances must
RESTORE before becoming valid again; heartbeat alone cannot revive stale counts.
STOP: removes only own counts/active requests and retains UUID/revision/high_water
in terminal state. Normal delta/HB/restore cannot revive a terminal writer.
SIGKILL has no cleanup; heartbeat staleness excludes contribution instead.

Reply: RESP2 [status integer, endpoint bulk string, count integer].
    -7 terminal/restoring, -6 expired, -5 resource limit, -4 revision mismatch,
    -3 corrupt, -2 invalid, -1 other writer, 0 stale/completed request,
     1 applied, 2 duplicate-confirmed, 3 released, 4 cancelled, 5 absent.
Control replies have empty endpoint/count 0. RELEASE/CANCEL return the original
endpoint when a mapping was found (otherwise empty); their count is always 0.
Transport completion/RESP error/absent owner is NOT successful admission.

Failure/resource boundaries
---------------------------
Callers explicitly supply instance/count-field/active-request budgets and a
maximum encoded wire size. These are API budgets, not invented deployment limits;
the old 4096-endpoint limit is not a 4096-connection limit. Bad types/arguments,
corrupt counts, overflow, exceeded budgets, UUID/revision mismatches fail without
normal writes. Resource/queue/deadline errors must fallback, not terminate TCPs.

Lua isolation is not rollback. Write errors attempt to mark this instance R;
even that invalidation can fail under ACL/OOM. Any error must fail-open to native
LC and require a fresh local restore. Do not keep heartbeat publishing a known
inconsistent state or claim immediate cancellation when the store is unavailable.
Lost release while an owner keeps sending HB needs pending cleanup/restore;
instance timeout alone cannot clean it. Network partition != process death.

Surviving old Pod + memory store loss cannot identify the legitimate UUID;
operator recovery is still required. START R2 remains documented, not solved.
No strict global accuracy is guaranteed in fallback/partition/uncertain writes.

------------------------

Step 2 adapter and native hooks (UD-005/007/009/010/011 v2-r2-20261003)
-----------------------------------------------------------------
USE_GLOBAL_LB includes global_lb_ledger.c/global_lb_dispatch.c and the client
deadline/kick APIs. USE_GLOBAL_LEASTCONN includes global_lb_select_v2.c, its
stream fields and native hooks. Common-only never activates a selector; OFF
has no new objects, fields, symbols or hooks. v1 behavior is preserved.

Each opted-in native slot has an immutable endpoint key and monotonic request
ID; connecting/established/fallback slots are captured, not queue entries.
Metadata follows sess_change_server(): a real old->new/NULL transition drops
the old entry; old==new does not drop it (native served duplicate adjustment
remains untouched). TCP success does not increment Global again. A selected
reserve whose native CAS fails/queues is cancelled; native dequeue can then
adopt a fallback slot, requiring a subsequent step-3 restore before Global/HB.

SC_ST_REQ waits only for this admission. A separate stream expiry and a capped
transport deadline retain the original queue+send+reply deadline through wrap-
safe HAProxy ticks. No conn_exp/SC_ST_QUE timeout is repurposed. Eligibility is
rebuilt on response; dynamic server pointers never survive an async wait.
Current health/backup/drain/maintenance and native slot capacity are checked.
The pre-connect key and actual allocated destination are compared too. Native
stats retain retry/redispatch accounting via numeric prior server identity.

Candidates are copied before taking the registry lock; encoding and I/O are
outside it. FIFO admissions/cleanup plus one in-flight command reuse the worker
transport. A coalesced kick wakes its task; lifecycle callback must service due
control commands before pump(), and must route REPLY/FAILED to dispatch_event()
only before handling control completions. No polling task or extra socket.
Task publication/destruction is serialized with cross-thread kicks.

Owner task pointers are detached under the registry lock before stream free.
A late successful TAKE is cancelled by its request ID. Queued unsent expired
requests are removed without an unnecessary -1. Unknown replies/transport
errors/failed local tracking invalidate Global, suppress future admissions/HB,
and retain uncertain cleanup until reconciliation. Healthy-connection cleanup
may continue while dirty; no unconfirmed TAKE is blindly replayed.

The serial capture API owns copies and checks a changes barrier at activation.
It includes native fallback/pending-connect slots and excludes incomplete
untracked slots. The worker-level bounded/coherent capture/restore integration,
production numeric budgets, heartbeat fairness and terminal policy belong to
step 3. In particular, the serial whole-copy API is NOT permission to allocate
or copy an arbitrarily large ledger under a long traffic-thread lock in step 3.
