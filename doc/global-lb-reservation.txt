Global LB v2: reservation protocol, lifecycle and read-only operations
====================================================================

User Define: UD-007/009/011 v2-r1-20261003; USE_GLOBAL_LB.
Configuration also implements UD-010 timer/migration validation.
This document supersedes v1 protocol assumptions only for reservation mode.

Implemented and not implemented
-------------------------------
Step 1 provides configuration, types, RESP2 builders/reply decoding and Lua.
Step 2 adds native stream/slot hooks, a serial metadata ledger and a dispatcher
on the EXISTING thread-0 client task. No extra task/thread/socket is created.
Step 3 (UD-006/007/008/010/011 v2-r3-20261003) activates the production worker
lifecycle: START, heartbeat, coherent native/fallback RESTORE and terminal STOP.
No EXTRA_OBJS test driver is needed. The old v1 publisher/collector is disabled
in v2; opted-in backends use Global only after confirmed coherent registration.
Step 4 (UD-012/016 v2-r4-20261004) adds copied read-only v2 diagnostics and
local system/burst regressions. Kubernetes/MetalLB deployment, full vtest,
complete sanitizer coverage and certified operating performance remain separate.

During this staged migration, configs containing only v1/common directives
retain v1 behavior. The compiled-in timer defaults remain reserve=100ms,
heartbeat=300ms and instance-timeout=3000ms, but selecting v2 requires at least
one v2-only timer or resource-limit directive. No new version
selector is invented. Mixing explicit v1 sync-interval/snapshot-ttl/stale-after/
recovery-successes with v2 timers is a configuration error, in either order.
The final v2 default-mode/migration switch is tracked separately, not silently
enabled by this step. Explicit v2 opt-in remains required for compatibility.

Reservation lifecycle contract
------------------------------
Reuse the native HAProxy flow, not a second local served implementation:
  1. Lua chooses the minimum eligible endpoint and increments its global
     reservation contribution, storing request-id -> endpoint atomically.
  2. HAProxy sets s->target, then follows native srv->served acquisition and
     sess_change_server()/s->srv_conn registration. Lua cannot atomically write
     the local C structures. Failure to acquire the native slot cancels the
     global reservation. Queue/maxconn/health/backup policy stays native.
  3. TCP success does not increment again. Global release follows native slot
     release, failure/redispatch/cancel/stream destruction exactly once.
     A same-server retry that retains its native slot must not release/reserve
     twice. A redispatch that changes assignment drops the old reservation.
The stream metadata tracks the remote request, not an independent local count.
Those hooks, asynchronous wait/resume, deadlines and fallback dispatch are
implemented in step 2; automatic startup/HB/recovery/shutdown is in step 3.
The original cur_sess/served read-only Local Snapshot fields stay unchanged.
Health-check connections and unassigned queue entries are not global reserves.

Configuration
-------------
See examples/global-lb-v2.cfg for the current production example. The historical
step1 example keeps its original100ms settings. New global directives:
    global-lb timeout reserve 1s
    global-lb timeout command 1s
    global-lb heartbeat-interval 300ms
    global-lb instance-timeout 3s
    global-lb max-instances 16
    global-lb max-requests 1024
All accept the native duration units/range used by the existing parser.
instance-timeout must be strictly greater than heartbeat-interval.
state-store and instance-id remain required if any global-lb setting is used.
Compiled-in connect=200ms, command=100ms, reconnect=100ms..5s, jitter=20% stay intact.
reserve timeout covers queued request + send + response and is wired in step 2.
Config changes require restart, not live reload. Default fallback is native LC.

UD-001/007/010/016 v2-timeouts-20261004: the production example and Helm chart
explicitly configure reserve=1s and command=1s for long-lived TCP admission.
The client uses the earlier of command expiry and the remaining reserve deadline;
these budgets are NOT additive. 300ms already queued leaves at most700ms for
send/reply, and a fast reply proceeds immediately. Backend connect time is
separate. C parser omission defaults are not changed, so no recompile is needed.
Heartbeat=300ms, instance-timeout=3s, connect=200ms, reconnect and the hard-coded
terminal cleanup100ms are unchanged. Existing100ms regression results are
historical; larger configured timeouts require their own burst/delay/HB checks.

Operating safety limits, not certified maximum performance:
  max-instances: group owner/liveness Hash fields, INCLUDING retained terminal
    owner records. Initial deployment expects 3 HAProxy instances; 16 is a
    configurable headroom default, NOT a native HAProxy process/thread limit.
  max-requests: group stored active reservation mappings (connecting + native
    established slots); default 1024 for expected ~100 group TCP connections.
    Stale crash mappings still consume physical capacity until own restart or
    explicit operator maintenance. Changing limits must be uniform per group.
  count-field safety ceiling: max-instances * 4096 instance/endpoint fields.
    This is not a 4096 connection cap or a count of services. Transport wire is
    capped at 8 MiB. Local ledger allows 2 * max-requests entries including
    uncertain cleanup; untracked native slots suppress incomplete restoration.
At resource/wire/allocation limits, log and stay on native local leastconn.
Application-level store limit replies cause clean reconnect/backoff. Existing
TCP remains alive. Native maxconn is separate; Global caps do not reject local
fallback traffic. Automatic stale physical reclamation is not implemented.

Storage schema (standalone Redis/Valkey, four fixed Hash keys)
------------------------------------------------------------
For key-prefix ipmdn:global-lb the keys are:
    glb:v2:69706d646e3a676c6f62616c2d6c62:owners
    glb:v2:69706d646e3a676c6f62616c2d6c62:liveness
    glb:v2:69706d646e3a676c6f62616c2d6c62:counts
    glb:v2:69706d646e3a676c6f62616c2d6c62:requests
Prefix and instance IDs are hex-encoded. v1 keys are disjoint and untouched.
All four accessed keys are supplied in EVAL KEYS; no generated Redis key access,
KEYS command or SCAN discovery in the selection path. This is not Cluster support.

Using i = hex(ipmdn-prod/haproxy-0):
    owners[i]                   = writer_generation UUID
    liveness[i]                 = revision|heartbeat_ms|high_water|A/R/D
    counts[i|be_ipmdn_tcp|10.244.1.10:5000] = 12
    requests[i|request_id]       = be_ipmdn_tcp|10.244.1.10:5000
A=active, R=requires restore, D=terminal. UUID is created once per worker process
startup and never changed on state-store reconnect. No AUTH/TLS/USE_LUA/hiredis.
TIME supplies the store clock; counts/requests have no short TTL that could erase
an active long-lived TCP connection. Stale instance contribution is ignored once
its heartbeat age exceeds the configured timeout. Physical stale instance/data
reclamation is a later maintenance concern; it is not claimed implemented here.

Protocol and idempotency
------------------------
START/RESTORE: supply all active request-id/endpoint assignments and high_water.
Derive own counts from that ledger and atomically replace only own contribution.
The caller must include pending native slot reservations and fallback assignments,
not only successful cur_sess connections. The caller captures them consistently
and serializes capture/commit/local changes; that stream ledger is not in step 1.
START can replace another UUID (accepted R2 delayed initial START limitation).
RESTORE registers a missing owner, but never steals another UUID's owner.
Same UUID/revision replacement retry confirms without overwriting later deltas.
Fresh RESTORE advances revision; every reserve/release/cancel/HB echoes it,
so delayed operations from before the replacement cannot change the new state.
STOP checks the UUID but deliberately tolerates an uncertain local revision;
after draining the command it excludes ONLY that writer and persists its fence.
Revisions are restore barriers, NOT newly generated writer UUIDs on reconnect.

RESERVE: candidates must be unique actual endpoint keys of one service/backend.
Only ACTIVE, fresh instances participate. Lua sums eligible endpoint counts,
chooses a minimum (equal weights; random ties seeded by caller), reserves +1 and
records its request ID. It returns the endpoint and global count after +1.
Duplicate active request returns its original endpoint/current global count
without +1, even if it is no longer in the refreshed candidate list; the caller
must revalidate health/identity and cancel instead of connecting if unsuitable.

RELEASE/CANCEL: a known request decrements once and removes its active mapping.
Unknown RELEASE is absent; unknown CANCEL advances the high-water fence. Released/
cancelled requests cannot be recreated by a delayed RESERVE. No completed-request
tombstone grows per connection: active mappings plus one monotonic per-writer
high_water are retained. New request IDs must increase at dispatch; out-of-order
older allocations may be rejected (safe fallback, not duplicate reservation).
IDs are not reset on reconnect. Duplicate active allocations remain replayable;
completed IDs <= high_water remain fenced. uint64 IDs/revisions are compared as
canonical decimal strings, preserving correctness above Lua's double precision.

HEARTBEAT: same UUID/revision and fresh ACTIVE state only. Expired instances must
RESTORE before becoming valid again; heartbeat alone cannot revive stale counts.
STOP: removes only own counts/active requests and retains UUID/revision/high_water
in terminal state. Normal delta/HB/restore cannot revive a terminal writer.
SIGKILL has no cleanup; heartbeat staleness excludes contribution instead.

Reply: RESP2 [status integer, endpoint bulk string, count integer].
    -7 terminal/restoring, -6 expired, -5 resource limit, -4 revision mismatch,
    -3 corrupt, -2 invalid, -1 other writer, 0 stale/completed request,
     1 applied, 2 duplicate-confirmed, 3 released, 4 cancelled, 5 absent.
Control replies have empty endpoint/count 0. RELEASE/CANCEL return the original
endpoint when a mapping was found (otherwise empty); their count is always 0.
Transport completion/RESP error/absent owner is NOT successful admission.

Failure/resource boundaries
---------------------------
Callers explicitly supply instance/count-field/active-request budgets and a
maximum encoded wire size. These are API budgets, not invented deployment limits;
the old 4096-endpoint limit is not a 4096-connection limit. Bad types/arguments,
corrupt counts, overflow, exceeded budgets, UUID/revision mismatches fail without
normal writes. Resource/queue/deadline errors must fallback, not terminate TCPs.

Lua isolation is not rollback. Write errors attempt to mark this instance R;
even that invalidation can fail under ACL/OOM. Any error must fail-open to native
LC and require a fresh local restore. Do not keep heartbeat publishing a known
inconsistent state or claim immediate cancellation when the store is unavailable.
Lost release while an owner keeps sending HB needs pending cleanup/restore;
instance timeout alone cannot clean it. Network partition != process death.

Surviving old Pod + memory store loss cannot identify the legitimate UUID;
operator recovery is still required. START R2 remains documented, not solved.
No strict global accuracy is guaranteed in fallback/partition/uncertain writes.

Step 2 adapter and native hooks (UD-005/007/009/010/011 v2-r2-20261003)
-----------------------------------------------------------------
USE_GLOBAL_LB includes global_lb_ledger.c/global_lb_dispatch.c and the client
deadline/kick APIs. USE_GLOBAL_LEASTCONN includes global_lb_select_v2.c, its
stream fields and native hooks. Common-only never activates a selector; OFF
has no new objects, fields, symbols or hooks. v1 behavior is preserved.

Each opted-in native slot has an immutable endpoint key and monotonic request
ID; connecting/established/fallback slots are captured, not queue entries.
Metadata follows sess_change_server(): a real old->new/NULL transition drops
the old entry; old==new does not drop it (native served duplicate adjustment
remains untouched). TCP success does not increment Global again. A selected
reserve whose native CAS fails/queues is cancelled; native dequeue can then
adopt a fallback slot, requiring a subsequent step-3 restore before Global/HB.

SC_ST_REQ waits only for this admission. A separate stream expiry and a capped
transport deadline retain the original queue+send+reply deadline through wrap-
safe HAProxy ticks. No conn_exp/SC_ST_QUE timeout is repurposed. Eligibility is
rebuilt on response; dynamic server pointers never survive an async wait.
Current health/backup/drain/maintenance and native slot capacity are checked.
The pre-connect key and actual allocated destination are compared too. Native
stats retain retry/redispatch accounting via numeric prior server identity.

Candidates are copied before taking the registry lock; encoding and I/O are
outside it. FIFO admissions/cleanup plus one in-flight command reuse the worker
transport. A coalesced kick wakes its task; lifecycle callback must service due
control commands before pump(), and must route REPLY/FAILED to dispatch_event()
only before handling control completions. No polling task or extra socket.
Task publication/destruction is serialized with cross-thread kicks.

Owner task pointers are detached under the registry lock before stream free.
A late successful TAKE is cancelled by its request ID. Queued unsent expired
requests are removed without an unnecessary -1. Unknown replies/transport
errors/failed local tracking invalidate Global, suppress future admissions/HB,
and retain uncertain cleanup until reconciliation. Healthy-connection cleanup
may continue while dirty; no unconfirmed TAKE is blindly replayed.

The serial capture API owns copies and checks a changes barrier at activation.
It includes native fallback/pending-connect slots and excludes incomplete
untracked slots. Production uses the step-3 incremental pinned-key walk and
batched commit, not the serial whole-copy helper under a traffic-thread lock.

Step 3 worker lifecycle (UD-006/007/008/010/011 v2-r3-20261003)
-----------------------------------------------------------
The existing post-fork worker writer/task owns one UUID and RESP2 connection.
Numeric/IPv6 and the existing nonblocking resolvers 'default' provider are
reused. No master-store client, OS thread, hiredis, AUTH or TLS was added.
Confirmed coherent START/RESTORE immediately enables Global (no 3-success
v1 rule). Until then, native local leastconn including pending connect slots
continues. START is submitted at most once, even if the reply is lost; RESTORE
can register the same UUID after memory loss, but cannot steal another UUID.
Owner/terminal mismatch latches local mode until restart/operator recovery.

Capture pins one entry under the short metadata lock, copies its immutable
endpoint outside the lock, and unpins. A registered cursor is repaired when
entries are removed, avoiding dangling stream/entry pointers. At most 32 entries
are captured/settled per task invocation; revision installation is also batched.
Native mutation/untracked slots during capture, encode, I/O or commit invalidate
the barrier. A new revision/current snapshot is required before local ACTIVE.
Pre-restore cleanup is consumed by replacement, never replayed against the new
revision. This avoids a long whole-ledger copy/encode lock, not all metadata
contention: inherited invalidation scans/slot allocation remain bounded by the
configured local ledger ceiling and require step-4 performance measurement.

Only heartbeat is periodic during healthy steady state. It refreshes liveness,
not counts. Dirty/failed reservations, fallback slots, lost releases, timeout
or memory-store restart require current local RESTORE BEFORE fresh HB/Global.
Due HB/control takes priority over one FIFO command without a second task.
Counts can be temporarily stale while a snapshot is in flight or while traffic
changes; a failed local barrier prevents local Global activation, but does NOT
make local C state and remote Lua one distributed atomic transaction. No exact
global count guarantee is claimed during recovery/fallback/network partition.

Terminal entry pauses frontend listeners and forbids Global admissions/HB/new
registration. Drain at most one in-flight command, then conditional UUID STOP
on that same connection, whole client cleanup deadline 100ms; never reconnect
or extend the timeout. Complete/failed cleanup resumes native terminal TCP
teardown through the existing signal queue. Local served/cur_sess are not zeroed.
SIGKILL has no STOP: stale contributions are excluded after 3s but physical
Hash fields remain. Old Pod/memory-loss and delayed START R2 exceptions persist.

Step 3's targeted tests alone were not Kubernetes/SRV/PPv2/splice certification.
Step 4's actual local SRV/PPv2/splice tests below do not certify a Kubernetes or
MetalLB deployment, either. No reload or automatic connection rebalance is added.

Step 4 read-only diagnostics (UD-012/016 v2-r4-20261004)
------------------------------------------------------
Build fences remain USE_GLOBAL_LB for common CLI/diagnostic helpers and
USE_GLOBAL_LEASTCONN for native selection hooks. Feature OFF has no new CLI,
objects, symbols, hooks or fields. Common-only does not start store I/O or a
selector. There is no new Prometheus metric, management write command, OS
thread, task, connection, Lua dependency, AUTH or TLS. Existing state-transition

The existing admin Runtime API now accepts:

    show global-lb reservations
    show global-lb local
Example with the example cfg's Unix socket (socat is an optional CLI client):
    printf '%s\n' 'show global-lb status' | socat - UNIX-CONNECT:/tmp/global-lb-admin.sock
    printf '%s\n' 'show global-lb reservations' | socat - UNIX-CONNECT:/tmp/global-lb-admin.sock

All three remain admin-only. No additional arguments are accepted by status or
reservations. The existing local table's backend/server/endpoint/oper_state/
cur_sess/served fields and native counter meanings are unchanged. The v1 status
and cache output format is preserved for v1 configs. In v2, 'show global-lb cache'
explicitly explains that periodic Global Cache does not exist and points to
status/reservations. It must not return a plausible empty v1 cache as v2 truth.
Reservations is v2-only; a v1 request receives a clear mode error.

Status fields:
  mode=v2-reservation; state=DISABLED/ACTIVE/FALLBACK/FENCED/STOPPING; usable.
  reason, transport, last_transport_error, instance-id, writer_generation.
  owner=confirmed/unconfirmed/fenced/not-registered; pending control operation;
  restore phase/revision, committed revision, last decoded control result.
  Confirmed heartbeat reply age and confirmed START/RESTORE activation age.
  Submitted START/RESTORE/HB totals, coherent activations, barrier retry total,
  transport failures and transport command timeouts; native ledger/queue counts.
  Current configured reserve/HB/instance timers and group safety ceilings.
  Existing shutdown/cleanup diagnostics, including the v2 UUID STOP result.
  Overlong instance-id display is clipped to 1024 bytes with an explicit
  instance-id-truncated flag; wire/config identity is NOT changed.

The status publisher previously returned an empty status without v1 registry
storage. That guard now recognizes an initialized v2 worker, so ACTIVE v2 does
not misleadingly report DISABLED/unknown UUID. Transport IDLE in common-only
means no connection/task was started, not store readiness.

Ownership is a LOCAL confirmed-registration observation, not a live query of
the remote owner UUID. Ages use wrap-safe local HAProxy milliseconds since a
confirmed reply; -1 means none. Store liveness continues to use Lua TIME and
the configured instance timeout, independently of these diagnostic ages.
Transport READY/COMMAND does not imply Global usable. A fresh local ledger
dirty flag immediately displays FALLBACK even before thread 0's next callback.
last_transport_error is historical and is not cleared by a successful reconnect.
last_control_result is the numeric protocol status, or unknown after no/invalid
control reply; it is not a globally current endpoint connection total.

Reservations is a fixed-size copied summary, NOT per-request/endpoint rows:
  entries = waiting + ready + native_slots + failed + cleanup.
  waiting/ready: admissions awaiting Lua result or native acceptance.
  native_slots: connecting/established/fallback slots already tracked locally.
  cleanup: detached metadata awaiting cleanup/replacement, not extra TCPs.
  queued_reserve/release/cancel: unsent FIFO commands; inflight is separate.
  admitted/reserve_confirmed/release_confirmed/cancel_confirmed are cumulative
  operation acknowledgements, not native served or actual +1/-1 totals.
  abandoned_unsent/sent includes invalidation/rejection and expiration, NOT
  only deadline timeouts. command_failures counts negative/uncertain replies.
  untracked blocks coherent recovery; dirty requires fresh restore; terminal
  fences new admissions. Neither count is repaired/reset by a CLI read.

Each ledger transition maintains O(1) state/queue tallies. A diagnostic read
copies only scalars under its short metadata lock: no entry iteration, string
allocation, native/server/stream pointer, pin or restore cursor mutation.
Thread 0 separately publishes a fixed-size lifecycle copy under its own lock.
CLI releases all locks before formatting/output; resumable 256-byte output
chunks preserve their initial copied text with small buffers/backpressure.
Lifecycle/ledger/transport are sampled separately, not one distributed or
cross-component atomic snapshot. Native counters are not duplicated or changed.

Operator interpretation and recovery
------------------------------------
An ACTIVE worker with usable=1 selects Global. FALLBACK/usable=0 means new
admissions use native local leastconn; existing TCPs survive. Inspect reason,
last_transport_error, dirty/untracked and restore/control state. Do not equate
a successful connect/PING or a recent HB display with completed recovery.

Transport/command errors: check private network reachability and store health;
the existing backoff reconnects with the same UUID and a fresh coherent RESTORE.
No CLI retry/reset/force-activate operation exists. Store memory loss follows
the same retained UUID/current native ledger recovery; no count-only replay.

FENCED: another writer/terminal owner rejected this process. First verify the
StatefulSet ordinal has no surviving old process/Pod. Restart/replace the
legitimate worker using the existing restart-only policy. Do not manually HSET
the owner, create a new UUID per reconnect or blindly delete another writer.
Delayed different-UUID initial START (R2) and surviving old Pod plus memory-store
loss remain accepted operational exceptions, not solved by this CLI.

Resource limits: log + local fallback, not process/TCP termination. Configure
uniform group max-instances/max-requests after assessing scale and wire limits.
STOP retains owner/liveness records. Crash contributions expire logically after
3s, but mappings/owner records still consume physical limits. There is no
automatic physical stale GC. Same-instance restart/STOP cleans only its own
records; a capacity issue from abandoned ordinals can persist.

Do not FLUSHDB/FLUSHALL or edit active group Hash fields to recover capacity.
If namespace reset is unavoidable, perform a coordinated maintenance stop of
ALL group workers, verify no surviving old processes/new traffic writers, and
remove ONLY that group's exact four versioned keys, then restart the group.
That is a destructive operator procedure, not an automatic runtime action.
Existing v1 keys and unrelated service groups must remain untouched. Never run
v1/v2 together expecting their separate key namespaces to yield one exact count.
